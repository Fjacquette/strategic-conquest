# Quirks, bugs and version differences

Each entry needs a decision: **reproduce** (match the original exactly) or **fix**.

| ID | Description | Source | Status | Decision |
|---|---|---|---|---|
| Q1 | Every piece created on a certain turn may move only one square on the turn it is created. Cause unknown to the developers. | 3.01 "Last Minute Notes": "We may have a bug that causes every piece created on a certain turn to only move one square on the turn that it's created. Call us if you figure out what causes it. (We may have fixed it, anyway.)" | Not yet located in code | Pending |
| Q2 | Combat and computer-opponent randomness is reseeded from the Mac's clock (seconds) at the end of every day, so outcomes depend on wall-clock time and a saved game does not continue the same random sequence. Proposed for the port: draw each day's seed from the server instead, which keeps the same distribution of outcomes and lets both browsers compute identical results. | `CODE 1 + 0x1F74`, see [findings.md](findings.md#randomness) | Confirmed in code | Pending |
| Q3 | Debug cheat: holding Option-W while an attack resolves forces a win; Option-L forces a loss. | `ResolveCombat`, `CODE 3 + 0x0004` (reads the keyboard with `_GetKeys`) | Confirmed in code | Pending (suggest: drop) |
| Q4 | When a Transport or Carrier in a city with an owner loses a fight, the code destroys the *first piece on that square in piece-table order* instead of the ship. If an Army or Fighter was created earlier and sits in the same city, it is destroyed and the ship survives. | `KillStack`, `CODE 3 + 0x0374`; reproduced in the emulator harness (Battleship sinks a Transport in its city: the Army in the city dies, the Transport survives) | Confirmed by running the original code | Pending (suggest: fix, destroy the ship) |
| Q5 | A Battleship-versus-Submarine column modifier is computed but never added, so Battleships get no bonus against Submarines. Probably a removed or unfinished rule; behavior is consistent either way. | `CODE 3 + 0x018C` | Confirmed in code | Pending (suggest: keep as is) |
| Q6 | When the piece table is full (449 pieces), the local player's new unit takes over the slot of an existing *opponent* piece: the highest-numbered unspotted Army, Fighter or Destroyer. Single player only. When the table is full and the other player builds, nothing is built, and the new-aircraft handling is applied to the last piece in the table instead. | `CODE 4 + 0x22E2` (verified by `tools/emu/test_units.py`) | Confirmed by running the original code; rarely reached | Pending (suggest: raise the limit, drop this) |
| Q7 | ~~Two-player speedups are not applied consistently in AppleTalk games.~~ Not a bug. Double repair and the faster Bomber radius test modes 1 and 2, while moves and build times test modes 1–3; the concern was that the Slave (mode 3) would apply the single-player rates. The Slave runs none of these rules: the Master (mode 2) runs both players' turns, so every speedup applies to both sides. See [network.md](network.md). | `CODE 5 + 0x4110`, `CODE 4 + 0x20EE` vs `CODE 4 + 0x11BA`, `CODE 1 + 0x021C`; Slave loop `CODE 10 + 0x1490` | Resolved: none of these routines is reachable from the Slave | None needed |
| Q8 | A Carrier is never reported full: the boarding check only refuses Armies boarding a full Transport, and its Carrier branch can never be reached. Fighters can keep landing on a Carrier, but when it moves it takes at most 15 of them along (those after it in the piece table) and leaves the rest in the air on the square it left. | `CODE 4 + 0x0D20`, `CODE 4 + 0x0F2C` | Confirmed in code (engine reproduces it) | Pending (suggest: fix, refuse the 16th Fighter) |
| Q9 | After a successful capture the game "looks around" the city using an uninitialised local piece record. Its type and position are stack leftovers, so whether an enemy Submarine next to the city is spotted, and which computer pieces wake, depend on leftovers. The engine uses an all-zero record (an Army at 0,0: Submarines are not spotted, nothing wakes). | `MoveArmy`, `CODE 5 + 0x2C98` | Confirmed in code and emulator | Pending (suggest: keep the engine's behavior) |
| Q10 | Code written for the computer opponent runs for every player-2 ship next to the map edge, before each step: the ship gets go-to orders to a random sea square 3–12 squares away. In a two-player game this overrides the human player 2's orders whenever a ship is in column 2 or 79 or row 2 or 59. | `PlayerTurn`, `CODE 5 + 0x47BE`, calling `CODE 6 + 0x0004` | Confirmed in code (engine reproduces it) | Pending (suggest: fix, apply to the computer only) |
| Q11 | When a computer player's piece under orders has an enemy (not an unspotted Submarine) beside it, the orders step leaves the direction unset and the piece steps in a direction made of stack leftovers. This only happens to player-2 ships given new orders by Q10. Usually the leftover is (0, 0) and the ship stays put; on the first step of a day, after repairs in port, it is part of a code address, which can throw the ship off the map. The engine uses (0, 0). | `CODE 5 + 0x1592` (enemy-adjacent branch), the movers' direction variables | Confirmed in the emulator | Pending (suggest: keep the engine's behavior) |
| Q12 | The five-to-one surrender rule is judged from the wrong side with two players on one Mac. It is meant for the computer: after day 100, a player other than the local one is beaten when player 1 has more than five times its cities, and against the computer that makes player 2 offer its surrender. On one Mac the local player at the end of the day is usually player 2 (the last player handed the Mac), so the rule is applied to player 1 instead: a player 1 holding more than five times player 2's cities after day 100 gets "I have smashed your forces. Tough luck!" and the game ends. | `Defeated`, `CODE 1 + 0x149A`; end checks at `CODE 1 + 0x1E16` | Confirmed by running the original code (11 cities against 1, day 101: with local player 2, player 1 is told it lost; with local player 1, player 2 offers its surrender) | Pending (suggest: fix, apply the rule to player 2 only, or to neither in two-player games) |
| Q13 | Wake wakes every piece on the clicked cell, the enemy's included, and the cell need not be explored or visible. A player can wake the enemy's sentries, pieces under go-to or patrol orders and loading Transports anywhere on the map, and the computer opponent or the other player then has to give them orders again. (Armies asleep aboard a Transport at sea go back to sleep on their own.) | `Domenu`, `CODE 16 + 0x02A0`, calling `CODE 4 + 0x0C08` | Confirmed in code and by running the original handler | Pending (suggest: fix, wake only the player's own pieces) |
| Q14 | Passwords (two-player games) keep only their first 5 characters, but checking one compares the whole password as typed, reading past the stored copy into unrelated memory. A password of 6 or more characters therefore probably fails every later check. | `CODE 2 + 0x3114`: stores 6 bytes of the typed Pascal string (length and 5 characters) and compares with `CODE 1 + 0x4E4C` over the typed length | Confirmed in code; not tried in the emulator | Pending (suggest: fix, limit passwords to 5 characters) |
| Q15 | A game resumed when the program starts (opened from the Finder, or with File > Resume Game before a game is under way) goes on one day later than it was saved. Games are saved at the start of a day, after the day count has gone up, and one resumed during a game goes on with that day; but at start-up the day loop counts the day up again before the first turn. Only the day number moves on (with what depends on it: the five-to-one surrender rule after day 100, and which days are autosaved). The browser game does the same for now. | Start screen `CODE 2 + 0x2C6A` loads the game, then `MainLoop` reaches its `day++` at `CODE 1 + 0x195C`; a resume during a game runs at `CODE 10 + 0x0A8A`, after that increment | Confirmed in code; a day-58 save resumed at start-up plays day 59 | Pending (suggest: fix, go on with the saved day) |
| Q16 | A computer Army waiting on its island for a loading Transport, and not next to one, is sent towards the nearest such Transport beside the island. If its first step that way would be onto water, it is meant to head instead for the shore beside that Transport, but the code records the number 1 where it means the Transport, so it heads for the shore beside piece 1 (the first Transport in the piece table, wherever it is) or, when piece 1 is not beside the island, for island 1's centre. | `CODE 7 + 0x103A` (`move.w #1, -$a(a6)`), used at `CODE 7 + 0x10EA` and `0x112C` | Confirmed in code; the engine's Army moves match the original's on recorded games | Pending (suggest: keep; it is how the original's computer plays) |
| Q17 | When a computer Army explores its island and none of the eight squares round it leads to unexplored ground, it looks for unexplored land 2 to 5 squares out, on square rings, in sight of the island's centre. The rings are centred on the square (x, x) instead of (x, y): the Army's column is passed for both coordinates, so the search looks in the wrong place except near the map's diagonal. | `CODE 7 + 0x0466`..`0x0492` (pushes the piece's x twice before calling `CODE 7 + 0x01EE`) | Confirmed in code; the engine's Army moves match the original's on recorded games | Pending (suggest: keep; it is how the original's computer plays) |
| Q18 | When the computer has fewer cities than it needs to go on the attack, an awake Bomber looks among the side's cities (not on the target island, within its fuel less five) for the one farthest from the enemy's centre. When none qualifies, the code goes on to read the chosen city's number, which it never set, from a stack leftover: if the leftover happens to be a city number (1-45) the Bomber flies to that city, otherwise to the side's nearest city. The engine uses 0, so such a Bomber flies to the nearest city. | `CODE 6 + 0x19D0` (the search, which clears its distance to 0 rather than 5000), read at `CODE 6 + 0x1B64` (`-$a(a6)`) | Confirmed in code; the harness clears the local on entry so the original and the engine agree | Pending (suggest: keep the engine's behavior) |
